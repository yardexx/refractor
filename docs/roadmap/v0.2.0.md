## Purpose

This file defines the exact scope of one concrete release.

If a feature is not defined here, it is not part of `v0.2.0`, even if it is
mentioned elsewhere in roadmap or feature docs.

## Release Goal

Ship a more trustworthy baseline release by focusing on correctness confidence,
shared infrastructure, and visible reporting around the existing rename and
string-encrypt passes.

## Scope Summary

`v0.2.0` contains seven feature areas:

1. merge correctness hardening work
2. expose pass statistics/reporting data
3. add the first generic reporter integration layer
4. add GitHub-oriented CI reporting
5. move const-context guard into shared transformer infrastructure
6. add a `strings`-based resistance test
7. improve architecture clarity for contributors and future pass work

## Feature Definitions

### 1. Merge Correctness Hardening

Goal:

- bring already identified rename correctness work into the release branch

Definition:

- merge the best available AST-node coverage improvements
- preserve runtime behavior across existing rename and string-encrypt flows
- keep the release scope limited to correctness, not new transform ideas

Acceptance criteria:

- relevant rename coverage work is present on the release branch
- existing unit and E2E tests pass
- no known regression is introduced by the merge itself

Required verification:

- targeted regression coverage for the merged handlers
- E2E smoke coverage for rename-only and rename-plus-string-encrypt builds

Out of scope:

- new rename features like overloading or randomized generation

### 2. Pass Statistics And Reporting Data

Goal:

- make pass work visible and measurable

Definition:

- passes return structured statistics or reports
- the build flow exposes those reports without embedding presentation logic
  into engine internals
- build results remain usable by later reporter features

Acceptance criteria:

- at least the current core passes expose structured metrics
- build results carry reports and failures through the full pipeline
- report data stays presentation-friendly without coupling engine logic to
  terminal formatting

Required verification:

- tests for report generation
- tests for build-result aggregation and fail-close behavior

Out of scope:

- reporter abstractions and output formatting beyond wiring the data through

### 3. Reporters

Goal:

- turn structured pass reports into generic plain-text build output

Definition:

- add the first dedicated rendering layer for build results
- move plain-text build formatting out of command logic
- keep engine report data presentation-neutral while making output readable

Acceptance criteria:

- plain-text formatting no longer lives directly in `BuildCommand`
- reporting behavior sits behind a clear abstraction
- reporter behavior has dedicated tests

Required verification:

- unit tests for reporter output or formatting decisions
- regression checks that build-result data stays presentation-neutral

Out of scope:

- server transport or hosted reporting
- GitHub-specific output integration

### 4. GitHub Reporter

Goal:

- make CI output more useful in GitHub Actions than plain local terminal output

Definition:

- add a GitHub-oriented reporter on top of the generic reporting seam
- keep GitHub-specific formatting out of `BuildCommand`
- preserve generic plain-text reporting for local use

Acceptance criteria:

- GitHub-oriented formatting does not live directly in `BuildCommand`
- the GitHub renderer consumes the same `BuildResult` data as the generic
  reporter
- reporter behavior has dedicated tests

Required verification:

- unit tests for GitHub-oriented formatting
- regression checks that generic rendering still works independently

Out of scope:

- Checks API integration
- hosted reporting or upload flows

### 5. Shared Const-Context Guard

Goal:

- stop reimplementing const-context tracking in individual transformers

Definition:

- move `_constDepth` and `_annotationDepth` tracking into shared pass
  transformer infrastructure
- make expression-transform passes inherit the same safety behavior by default

Acceptance criteria:

- string-encrypt behavior remains correct after the move
- shared guard is used from the common transformer layer
- tests cover const and annotation contexts

Required verification:

- unit coverage for const and annotation skipping
- regression check for current string-encrypt behavior

Out of scope:

- adding new expression transforms in this release

### 6. `strings` Resistance Test

Goal:

- validate obfuscation effectiveness against a real and cheap inspection tool

Definition:

- compile a representative fixture
- obfuscate it
- run `strings` on the produced native artifact
- assert that protected plaintext identifiers and strings do not leak

Acceptance criteria:

- the test runs in the normal verification path or a clearly documented
  security-focused path
- expected allowlist and denylist behavior is explicit
- test failures are actionable, not noisy

Required verification:

- one working fixture with known identifiers and strings
- clear assertions for forbidden plaintext leakage

Out of scope:

- Blutter-based heavy resistance testing

### 7. Architecture Clarity

Goal:

- make the current codebase easier to understand and extend safely

Definition:

- refresh architecture docs to match current code
- make the pass-construction path more explicit for contributors
- reduce hidden complexity in rename-pass orchestration when practical

Acceptance criteria:

- architecture docs no longer describe removed pass-system shapes as current
- contributors can trace how a new pass is configured and instantiated
- any targeted readability refactors preserve existing behavior and tests

Required verification:

- doc/code alignment review
- regression tests for any refactored behavior-sensitive paths

Out of scope:

- plugin infrastructure
- broad framework rewrites that do not improve near-term execution clarity

## Release Blockers

Do not treat `v0.2.0` as ready unless all of these are true:

- core tests pass
- new or changed behavior has tests
- release scope is still limited to the seven defined feature areas
- any deferred item is explicitly deferred, not silently dropped

## Not In `v0.2.0`

Even if other docs mention them, these are not part of this release:

- interpolation support for string encryption
- multi-layer string encoding
- name overloading
- randomized name generation
- symbolicate command
- Crashlytics compatibility
- dry-run mode

## Exit Rule

When `v0.2.0` ships, keep this file as the historical release definition and
create the next concrete release file for the next release under active work.
