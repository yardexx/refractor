This file is the overview for the whole `v0.2.x` version line.

Use it for:

- what `v0.2.x` is trying to achieve overall
- all features planned for `v0.2.x`
- sequencing and dependencies across patch releases
- what is explicitly deferred beyond `v0.2.x`

Do not put detailed feature definitions here. Those belong in the concrete
release file for the next release, or in a dedicated feature spec.

## Outcome We Want From v0.2.x

`v0.2.x` should make Refractor credible as a practical obfuscation tool for
existing rename and string-encrypt use cases.

By the end of `v0.2.x`, we want:

- stronger correctness confidence
- better build and pass reporting
- cleaner engine architecture
- better reproducibility and naming behavior
- a clear path for symbolication and crash-reporting workflows

## Current Baseline Before Post-`0.2.0` Planning

Already implemented in code:

- rename correctness hardening and E2E smoke coverage
- seeded shuffled rename generation
- static and constructor-related rename safety
- string-encrypt baseline with per-string keys
- symbol-table IO outside the engine layer

Still active in `v0.2.0`:

- const-context guard in shared transformer infrastructure
- pass statistics/reporting
- resistance-test coverage

## Suggested Patch-Level Sequencing

### `v0.2.0`

Concrete next release. Scope is defined in [v0.2.0.md](v0.2.0.md).

### `v0.2.1`

String-encryption hardening release.

Candidate scope:

- interpolation handling
- decode helper pragma
- multi-layer encoding
- Unicode regression tests

Why this version next:

- it builds directly on the existing string-encrypt baseline
- it strengthens the most visible current differentiator
- it has clear testable outcomes without needing broad architecture churn

Primary feature references:

- [../features/future/string-encrypt-improvements.md](../features/future/string-encrypt-improvements.md)
- [../features/future/string-interpolation-handling.md](../features/future/string-interpolation-handling.md)
- [../features/future/decode-helper-never-inline.md](../features/future/decode-helper-never-inline.md)
- [../features/future/multi-layer-encoding.md](../features/future/multi-layer-encoding.md)

Exit criteria:

- interpolation support lands with regression tests
- decode helper indirection is hardened in tested modes
- multi-layer encoding is working and Unicode-safe
- `v0.2.0` reporting/resistance work is still green after the changes

### `v0.2.2`

Rename hardening and remaining engine-cleanup release.

Candidate scope:

- name overloading
- pass-construction and architecture cleanup
- mapping stability policy
- keep-name controls or at least a clear design-ready doc if they are not yet
  ready to implement

Primary feature references:

- [../features/future/01-name-overloading.md](../features/future/01-name-overloading.md)
- [../features/future/rename-improvements.md](../features/future/rename-improvements.md)

Why this version after `v0.2.1`:

- rename is already functionally stronger than the docs suggested
- the remaining rename work is now more about safe hardening and operator policy
  than about baseline correctness
- it benefits from having the `v0.2.0` and `v0.2.1` verification foundation in
  place first

Open planning note:

- if name overloading proves too large or risky, split pass-construction cleanup and
  mapping policy work into this version and push overloading one version later

### `v0.2.3`

Crash-reporting and developer-experience release.

Candidate scope:

- symbolicate command
- Crashlytics compatibility
- artifact-handling boundary
- public-facing docs
- dry-run mode

Primary feature references:

- [../features/future/02-dry-run.md](../features/future/02-dry-run.md)
- [../features/future/03-symbolicate.md](../features/future/03-symbolicate.md)
- [../features/future/04-crashlytics-symbol-format.md](../features/future/04-crashlytics-symbol-format.md)
- [../features/future/05-artifact-handling.md](../features/future/05-artifact-handling.md)

Why this version after `v0.2.2`:

- symbolication becomes more valuable once naming behavior and symbol artifacts
  are more settled
- artifact handling becomes more valuable once multiple output types exist
- `dry-run` benefits from pass statistics/reporting already being available
- this version can focus on operator workflows rather than core transform logic

Exit criteria:

- stack traces can be symbolicated locally
- at least one practical crash-report symbol workflow is documented or
  implemented
- `dry-run` provides useful pre-build visibility without breaking normal builds

## Dependencies Inside v0.2.x

- shared const-context guard helps later expression-transform features too
- pass reporting and build artifacts support later DX work
- rename hardening and mapping behavior should settle before advanced
  symbolication workflows
- crash-reporting work depends on stable and trustworthy symbol artifacts
- string-encrypt hardening should land before string-array indirection or
  deduplication policy work

## Explicitly Deferred Beyond v0.2.x

These do not belong in the active `v0.2.x` scope:

- control-flow flattening
- arithmetic substitution
- method outlining
- misleading-name strategies
- DevTools extension work
- package distribution mode
