# Refractor v0.2 — Feature Goals

## Overview

Version 0.2 focuses on significantly strengthening obfuscation passes and adding new ones. The current passes (rename, string_encrypt) provide a baseline but have known weaknesses that a motivated reverser can defeat quickly. This version aims to close those gaps and introduce new transformation categories.

> **Prerequisite reading:** [optimization-resistance.md](optimization-resistance.md) — analysis of the Dart VM's CFG optimizer pipeline. Every proposed technique must survive these passes to provide real obfuscation value.

---

## 0. Optimization Resistance Principles

Every obfuscation technique must survive the Dart VM's CFG optimization pipeline to provide value in compiled output. Key rules:

1. **Never produce all-constant expressions** — the Simplification pass folds them. Always include a runtime-derived operand.
2. **Use `@pragma('vm:never-inline')`** on injected procedures — prevents the AOT compiler from inlining helpers back into callers.
3. **Structural transforms are inherently safe** — rename, outlining, and string indirection change program structure, not expressions. They always survive.
4. **Both branches must be live** — for control flow obfuscation, ensure both paths contain code with observable side effects. Dead branches are eliminated regardless of predicate complexity.
5. **Runtime state defeats constant propagation** — variables written from multiple branches cannot be resolved to a single constant value.

Full analysis: [optimization-resistance.md](optimization-resistance.md)

## 1. Improve Existing Passes

### 1.1 Rename Pass — Expand Scope

**Current state:** Renames classes, fields, and procedures. Does not touch local variables, parameters, constructors, or static member references.

**Goals:**
- [ ] Rename local variables and parameters (safe because kernel uses identity-based references, not name strings, for `VariableGet`/`VariableSet`)
- [ ] Handle static member call sites (`StaticGet`, `StaticSet`, `StaticInvocation`) — currently only instance dispatch is updated
- [ ] Handle constructor invocations
- [ ] Name overloading — reuse the same short name across unrelated classes (ProGuard-style) to defeat search-replace deobfuscation
- [ ] Randomize name generation instead of deterministic `_$0, _$1, _$2` sequence (optional seed for reproducibility)

### 1.2 String Encrypt Pass — Strengthen Encryption

**Current state:** Single-byte XOR with a fixed key across all strings. Key is visible as an `IntLiteral` at every call site. `StringInterpolation` nodes are not handled.

**Goals:**
- [ ] Per-string random keys (trivial change — randomize `xorKey` per `visitStringLiteral`)
- [ ] Multi-layer encoding: XOR + byte reversal + Base64 (injected decoder chains transformations)
- [ ] String array with index indirection — extract all strings into a global shuffled `List<String>`, replace each use with `_obfStr$(index)` (hides string-to-usage association)
- [ ] Consider RC4 stream cipher as an alternative to XOR (injectable as ~20 kernel statements, much stronger than single-byte XOR)
- [ ] Handle `StringInterpolation` — encrypt the literal parts within interpolations

### 1.3 Dead Code Pass — REMOVED

The dead_code pass was removed in v0.2. The Dart VM's CFG optimizer (ConstantPropagation + ControlFlowOptimizations) eliminates all inserted dead branches — including `identical([], [])` predicates — because the branch bodies have no observable side effects. See [optimization-resistance.md](optimization-resistance.md) for full analysis.

Future control flow obfuscation should use techniques where both branches contain observable side effects (CFF, bogus control flow with cloned real code).

## 2. New Passes

### 2.1 Control Flow Flattening (`control_flow_flatten`) — **VIABLE** (optimization-resistant)

> **Optimization resistance:** CFF survives because the state variable is written from multiple branches — ConstantPropagation cannot resolve it to a single constant. Use `@pragma('vm:never-inline')` on the dispatcher if extracted into a separate procedure.

**What:** Transform procedure bodies into a state-machine dispatch loop. All basic blocks become cases in a `switch` inside `while(true)`, connected by a state variable.

```
// Before:
if (x > 0) { A(); } else { B(); }
C();

// After:
var _s = 0xA1B2;
while (true) {
  switch (_s) {
    case 0xA1B2: _s = x > 0 ? 0xC3D4 : 0xE5F6; break;
    case 0xC3D4: A(); _s = 0x7890; break;
    case 0xE5F6: B(); _s = 0x7890; break;
    case 0x7890: C(); return;
  }
}
```

**Details:**
- Linearize AST into basic blocks, assign random state IDs
- Encode state transitions (`switch(_s ^ mask)`) to defeat pattern matching
- Skip `async`/`async*`/`sync*` procedures (already lowered to state machines)
- Skip procedures with `TryCatch`/`TryFinally` (exception semantics require structured nesting)
- Mark injected helpers with `@pragma('vm:never-inline')` to prevent AOT from undoing the transformation
- Config: enable per-procedure via name patterns, or globally with exclusions

**Impact:** High protection, high performance cost (1.5–4x in tight loops, negligible for I/O-bound code). Apply selectively.

### 2.2 Instruction Substitution (`arithmetic`)

**What:** Replace simple arithmetic/logic operations with semantically equivalent but complex expressions using Mixed Boolean-Arithmetic (MBA) identities.

```
// Before:
a + b

// After (MBA identity):
(a ^ b) + 2 * (a & b)
```

**Substitution rules:**
- `a + b` → `(a ^ b) + 2 * (a & b)`
- `a - b` → `(a ^ b) - 2 * (~a & b)`
- `a & b` → `~(~a | ~b)` (De Morgan)
- `a | b` → `~(~a & ~b)`
- Integer literal `n` → `(n ^ k) ^ k` with random `k`

**Details:**
- Transform `InstanceInvocation` nodes for `+`, `-`, `&`, `|`, `^` operators
- Configurable substitution depth (1–2 iterations, deeper = exponential blowup)
- Skip const contexts

**Impact:** Low performance cost at depth 1. Medium protection — defeats casual reading, not symbolic execution.

### 2.3 Method Outlining (`outline`)

**What:** Extract slices of statements from procedure bodies into new synthetic procedures, replacing them with calls.

```
// Before:
void process() {
  setup();
  computeA();
  computeB();
  cleanup();
}

// After:
void _$7() { computeA(); computeB(); }
void process() {
  setup();
  _$7();
  cleanup();
}
```

**Details:**
- Analyse variable liveness — captured variables become parameters of the extracted procedure
- Return values handled via out-parameters or function return
- Mark extracted procedures with `@pragma('vm:never-inline')`
- Config: extraction probability, min/max statements per extraction

**Impact:** Low performance cost. Medium protection — fragments logical units, especially effective combined with rename.

### 2.4 Integer Constant Encoding (`number_encode`) — **WEAK** without runtime key

> **Optimization resistance warning:** If both operands of `(n ^ k) ^ k` are `IntLiteral`, the Simplification pass folds them back to `n`. Only viable with runtime key laundering (a `final` field or variable read), which adds real runtime cost.

**What:** Replace integer literals with runtime expressions that compute the same value.

```
// Before:
int timeout = 30000;

// After:
int timeout = (0x7530 ^ 0xCAFE) ^ 0xCAFE;  // computes to 30000
```

**Details:**
- XOR split: `n` → `(n ^ k) ^ k` with random `k`
- MBA encoding: use invertible polynomial functions over 64-bit integers
- Skip const contexts (constants cannot contain function calls)
- Use runtime anchoring (e.g., involve a `DateTime.now()` derived value) to prevent AOT constant folding — optional, adds real runtime cost

**Impact:** Negligible performance cost. Low-medium protection — noise layer, useful in combination.

## 3. Infrastructure Improvements

### 3.1 Pass Context Cleanup

**Current issue:** `PassContext` imports `dart:io` (reads `Directory.current` and `pubspec.yaml` at construction time), violating the engine's "zero dart:io" contract.

**Goal:** Extract IO-dependent initialization into the caller. `PassContext` should receive a `projectPackageName` string and `projectRoot` URI, not read them from disk.

### 3.2 Configurable Pass Ordering

**Current state:** Passes run in list order. No explicit ordering constraints.

**Goal:** Document and enforce recommended ordering:
1. `rename` (first — other passes generate new identifiers that shouldn't be renamed)
2. `string_encrypt` (before control flow passes that might move string literals)
3. `number_encode` / `arithmetic` (before control flow passes)
4. `dead_code` / `control_flow_flatten` / `outline` (structural passes last)

### 3.3 Pass Statistics and Reporting

**Current state:** Some passes track counts internally but never surface them.

**Goal:** Each pass reports metrics (nodes transformed, procedures skipped, etc.) via a structured `PassResult` returned from `Pass.run()`. The CLI displays a summary table after build.

### 3.4 Const-Context Guard as Shared Infrastructure

**Current state:** `StringEncryptTransformer` manually tracks `_constDepth` and `_annotationDepth`. Any new pass that transforms expressions needs the same logic.

**Goal:** Move const-context tracking into the `PassTransformer` base class so all passes automatically inherit it.

## 4. Priority and Phasing

### P0 — Foundation
- [x] Remove dead_code pass (eliminated by VM optimizer — see [optimization-resistance.md](optimization-resistance.md))

### P1 — Quick wins (high value, low effort)
- Local variable renaming
- PassContext dart:io cleanup
- Static call site handling in rename
- Constructor invocation handling in rename

### P2 — Significant improvements (medium effort)
- String array with index indirection
- Multi-layer string encoding
- Instruction substitution (MBA, depth 1-2) — **VIABLE**
- Method outlining — **VIABLE** with `@pragma('vm:never-inline')`
- Name overloading
- Pass statistics/reporting
- Const-context guard in base class

### P3 — Major new capabilities (high effort)
- Control flow flattening — **VIABLE** (runtime state variable)
- RC4 string encryption
- Randomized name generation

### P4 — Future consideration (requires further research)
- Dead code / bogus control flow — **WEAK** unless both branches have side effects
- Integer constant encoding — **WEAK** unless runtime-laundered
- Class merging/splitting
- Anti-debug timing checks
- Environment detection checks

## 5. Non-Goals for v0.2

- **AES encryption** — injecting a full AES implementation as kernel AST is impractical
- **Binary integrity checks** — cannot compute checksum of final binary at kernel obfuscation time
- **Array data transformation** — requires whole-program type analysis, high complexity for low payoff
- **Web target support** — Dart's 53-bit int precision on dart2js breaks many bitwise tricks; defer to a later version
