## 1. Opaque Predicates

### What is it?

An opaque predicate is a conditional expression whose result is known at obfuscation time but is difficult or impossible for a static analyser to determine. It replaces an obviously-true or obviously-false condition with one that *looks* like it could go either way.

### Why the current approach is weak

The current dead_code pass uses:

```dart
if (false) { /* junk */ }
```

`BoolLiteral(false)` is a compile-time constant. The Dart VM, AOT compiler, and any decompiler will immediately constant-fold it away. The dead branch literally disappears from the compiled output.

### Stronger alternatives

**Category 1 — Allocation identity:**

```dart
if (identical(<int>[], <int>[])) { /* dead */ }
```

`identical()` checks reference equality. Two separate list allocations always produce distinct objects, so this is always `false`. But a static analyser cannot prove this without modelling the heap — it would need to know that `[]` allocates a fresh object every time, which is an implementation detail of the runtime.

Why it works: `identical` is a built-in that compares object pointers. The analyser sees two expressions of the same type and cannot statically determine whether they alias the same object.

**Category 2 — Number theory:**

```dart
// Product of consecutive integers is always even
if ((x * (x + 1)) % 2 != 0) { /* dead */ }
```

For any integer `x`: either `x` or `x+1` is even, so their product is always even, and `% 2` is always `0`. A symbolic execution engine *can* prove this, but it requires modular arithmetic reasoning that most decompilers don't perform.

Stronger variant — use a runtime-derived `x`:

```dart
final x = DateTime.now().microsecondsSinceEpoch;
if ((x * (x + 1)) % 2 != 0) { /* dead */ }
```

Now `x` is not a constant, so AOT constant folding cannot eliminate it.

**Category 3 — Collatz conjecture:**

```dart
int n = <some runtime value>;
while (n != 1) {
  n = n.isEven ? n ~/ 2 : 3 * n + 1;
}
// n is now always 1
if (n != 1) { /* dead */ }
```

The Collatz conjecture states this always terminates at 1. It is unproven in general but verified for all values up to ~10^20. No static analyser can simplify this — it would need to solve an open problem in mathematics.

Trade-off: the loop actually executes at runtime, adding real cost. Use a small seed value (e.g., seed from 2–100) where the sequence is short.

### How it maps to kernel AST

```
// identical([], [])
StaticInvocation(
  target: dart:core::identical,
  arguments: Arguments([
    ListLiteral([], typeArgument: InterfaceType(int)),
    ListLiteral([], typeArgument: InterfaceType(int)),
  ])
)
```

The `identical` function is a top-level procedure in `dart:core`. Resolve it from `Component.libraries` where `importUri == 'dart:core'`, find the procedure named `identical`.

### Optimization resistance

**Verdict: WEAK.** The Dart VM's ConstantPropagation + ControlFlowOptimizations eliminate dead branches whose bodies have no observable side effects — regardless of predicate complexity. Even `identical([], [])` is resolved. Opaque predicates alone are insufficient; they must guard branches that contain real, side-effectful code. See [optimization-resistance.md](optimization-resistance.md).

## 2. Bogus Control Flow

### What is it?

Bogus Control Flow (BCF) is a superset of opaque predicates. Instead of just inserting dead branches with junk code, BCF *clones* real basic blocks and connects the clone and the original through an opaque predicate. The result is two paths through the code that appear equally valid to a reverser.

### How it differs from simple dead code insertion

```
// Simple dead code (current approach):
realCode();
if (opaqueFalse) { junk(); }

// Bogus control flow:
if (opaqueTrue) {
  realCode();    // <-- actually executed
} else {
  realCodeClone(); // <-- clone of real code, never executed
}
```

In the BCF version, a decompiler shows two plausible execution paths. The reverser must determine which branch is taken — and with a good opaque predicate, that requires dynamic analysis (actually running the code).

### Strength considerations

BCF is stronger when:
- The cloned code is slightly mutated (different constant values, reordered statements) so it's not a byte-for-byte copy
- Combined with rename (both paths use the same obfuscated names)
- Applied multiple times (nest BCF blocks)

BCF is weaker when:
- Dynamic analysis is available (just run the program and trace which branches execute)
- The opaque predicate is weak (e.g., `if (false)`)

### Optimization resistance

**Verdict: WEAK unless both branches contain side effects.** If the dead branch body has no observable side effects, the optimizer removes it regardless of predicate strength. BCF is only viable when the cloned code in the false branch contains real function calls or state mutations that the optimizer cannot prove dead. See [optimization-resistance.md](optimization-resistance.md).

### Further reading

- OLLVM BCF implementation: https://github.com/obfuscator-llvm/obfuscator/wiki/Bogus-control-flow
- O-MVLL (mobile-focused LLVM obfuscator) documentation on BCF: https://obfuscator.re/omvll/passes/control-flow-flattening/

## 3. Control Flow Flattening

### What is it?

Control Flow Flattening (CFF) is the most powerful structural obfuscation technique in common use. It destroys the natural nesting structure of code (if/else, for, while) and replaces it with a flat state machine.

### The transformation

**Original code:**

```dart
void process(int x) {
  var result = 0;           // Block A
  if (x > 0) {
    result = x * 2;         // Block B
  } else {
    result = x * -1;        // Block C
  }
  print(result);            // Block D
}
```

**Natural control flow graph:**

```
    [A]
   /   \
  v     v
 [B]   [C]
  \   /
   v v
   [D]
```

**After flattening:**

```dart
void process(int x) {
  var result = 0;
  var _state = 0x3A7F;     // entry state

  while (true) {
    switch (_state) {
      case 0x3A7F:          // Block A: evaluate condition
        _state = (x > 0) ? 0x1B2C : 0x4D5E;
        break;
      case 0x1B2C:          // Block B
        result = x * 2;
        _state = 0x6F70;
        break;
      case 0x4D5E:          // Block C
        result = x * -1;
        _state = 0x6F70;
        break;
      case 0x6F70:          // Block D
        print(result);
        return;
    }
  }
}
```

**Flattened control flow graph:**

```
       ┌──────────────┐
       │  dispatcher   │ <───────┐
       │ switch(_state)│         │
       └──┬──┬──┬──┬──┘         │
          │  │  │  │             │
          v  v  v  v             │
         [A][B][C][D]            │
          │  │  │                │
          └──┴──┴────────────────┘
                    (_state = next)
```

All blocks are now siblings at the same nesting level. The original structure (A→B/C→D) is encoded only in the state variable transitions, which are integer assignments scattered across switch cases.

### Why it's effective

1. **Decompilers fail.** Most decompilers reconstruct high-level structure by analysing the control flow graph for patterns like "diamond" (if/else) and "back edge" (loops). CFF produces a single loop with a single switch — no diamonds, no nested loops. The decompiler output is the flat switch itself, which is unreadable.

2. **Static analysis is expensive.** To recover the original structure, an analyser must perform "deflattening" — tracing all possible values of `_state` through the switch. This is equivalent to solving a reachability problem on the state space, which is O(n^2) in the number of blocks and requires symbolic execution.

3. **State encoding makes it harder.** Instead of `switch (_state)`, use `switch ((_state * 0x5DEECE66D + 0xB) & 0xFFFFFFFF)` (a linear congruential generator). The reverser must now invert the LCG to determine state transitions.

### Challenges for Dart kernel

**AST vs CFG:** Dart kernel is a structured AST, not a CFG (control flow graph). You must convert AST→blocks→switch, which means:
- Sequential statements in a `Block` become individual cases
- `IfStatement` is split: condition-check in one case, then-branch and else-branch in separate cases
- `ForStatement` / `WhileStatement`: the condition-check becomes a case that loops back (sets `_state` to itself on continue, to next on exit)
- `ReturnStatement` terminates — the case just returns directly
- `BreakStatement` / `ContinueStatement` with labels need careful mapping to state transitions

**Exception handling:** `TryCatch` and `TryFinally` cannot be flattened. Dart requires structured nesting for exception semantics (the runtime needs to know the try-block boundaries). These must be left as-is inside their respective switch cases.

**Async procedures:** Already lowered to state machines by the Dart frontend. Flattening them would produce a state machine inside a state machine — possible but adds complexity for little gain. Skip them.

### Optimization resistance

**Verdict: VIABLE.** CFF survives optimization because the state variable is written from multiple switch cases — ConstantPropagation cannot resolve it to a single constant. The dispatcher loop and switch structure are preserved in compiled output. For maximum resistance, mark any extracted dispatcher procedure with `@pragma('vm:never-inline')`.

- Laszlo, Kiss — "Obfuscating C++ Programs via Control Flow Flattening" (2009): https://www.inf.u-szeged.hu/~laszlot/publications/cff_2009.pdf

## 4. Mixed Boolean-Arithmetic (MBA)

### What is it?

MBA expressions combine standard arithmetic (+, -, *) with bitwise Boolean operations (&, |, ^, ~) in ways that are algebraically equivalent to simple expressions but extremely hard to simplify automatically.

### Foundation: bitwise arithmetic identities

These identities hold for all integers in two's complement representation (which Dart uses on native targets):

```
a + b  ==  (a ^ b) + 2 * (a & b)
a - b  ==  (a ^ b) - 2 * (~a & b)
a & b  ==  ~(~a | ~b)              // De Morgan
a | b  ==  ~(~a & ~b)              // De Morgan
a ^ b  ==  (a | b) & ~(a & b)     // XOR definition
  -a   ==  ~a + 1                  // Two's complement negation
```

### Why they're hard to simplify

Consider `(a ^ b) + 2 * (a & b)`. A human recognises this as `a + b`, but an automated simplifier must:

1. Know that `^` and `&` distribute over `+` in this specific pattern
2. Try all possible factorings of the expression
3. Handle nested MBA (the result of one substitution is itself substituted)

At depth 2 (substitute the result once more), `a + b` becomes:

```
((a ^ b) ^ (2 * (a & b))) + 2 * ((a ^ b) & (2 * (a & b)))
```

This is 11 operations instead of 1. At depth 3, it explodes further. Tools like MBA-Blast (USENIX 2021) can handle *linear* MBA, but non-linear MBA (involving multiplication of variables) remains an open problem.

### Practical application in Dart kernel

When the transformer visits an `InstanceInvocation` node for operator `+` on two integer expressions:

```
// Original kernel AST:
InstanceInvocation(
  receiver: VariableGet(a),
  name: Name('+'),
  arguments: Arguments([VariableGet(b)])
)

// Substituted:
// (a ^ b) + 2 * (a & b)
InstanceInvocation(
  receiver: InstanceInvocation(
    receiver: VariableGet(a),
    name: Name('^'),
    arguments: Arguments([VariableGet(b)])
  ),
  name: Name('+'),
  arguments: Arguments([
    InstanceInvocation(
      receiver: IntLiteral(2),
      name: Name('*'),
      arguments: Arguments([
        InstanceInvocation(
          receiver: VariableGet(a),
          name: Name('&'),
          arguments: Arguments([VariableGet(b)])
        )
      ])
    )
  ])
)
```

Important: `VariableGet(a)` and `VariableGet(b)` must reference the *same* `VariableDeclaration` objects as the original — do not create new declarations or you'll break the reference chain.

### Depth control

Substitution depth must be configurable (1 or 2). Each level roughly triples the AST node count for arithmetic expressions. At depth 3+, the AST becomes enormous and compilation time suffers.

### Optimization resistance

**Verdict: VIABLE at depth 1-2.** MBA expressions survive the optimizer when at least one operand is a runtime variable (not a literal). At depth 1, the expression tree is small enough that Simplification does not reduce it. At depth 3+, the Simplification pass may partially fold sub-expressions with constant operands. Never use all-literal operands — always include at least one `VariableGet`.

- Zhou, Banescu et al. — "MBA-Blast: Unveiling and Simplifying Mixed Boolean-Arithmetic Obfuscation" (USENIX Security 2021): https://www.usenix.org/conference/usenixsecurity21/presentation/liu-binbin
- Plzin — "Mixed Boolean-Arithmetic (Part 1): Introduction" — excellent practical walkthrough: https://plzin.github.io/posts/mba

## 5. String Array Indirection

### What is it?

Instead of encrypting each string in-place, all strings in the program are extracted into a single global array. Each original string usage is replaced with an indexed lookup into that array.

### The transformation

**Before:**

```dart
print("hello");
var name = "world";
throw Exception("something went wrong");
```

**After:**

```dart
// Injected global array (shuffled + encrypted):
final _obfArr$ = [
  _decode("...encrypted 'something went wrong'..."),
  _decode("...encrypted 'hello'..."),
  _decode("...encrypted 'world'..."),
];

print(_obfArr$[1]);
var name = _obfArr$[2];
throw Exception(_obfArr$[0]);
```

### Why it's effective

1. **Breaks string-to-usage association.** A reverser can no longer `grep` the binary for "error" or "password" and jump to the relevant code. All strings live in one array far from their use sites.

2. **Shuffling defeats index guessing.** The array order does not match the order strings appear in source. Index `0` might be the last string in the program.

3. **Combined with encryption.** Each element in the array can itself be XOR-encrypted or multi-layer encoded. The reverser must first decrypt the array, then figure out which index maps to which usage.

### Index encoding (optional enhancement)

Instead of plain integer indices, encode the index:

```dart
// Plain: _obfArr$[5]
// Encoded: _obfArr$[(5 * 7) % arrayLength]  // modular arithmetic
// Or: _obfArr$[5 ^ 0xCAFE]  // XOR with a key baked into the lookup helper
```

The lookup helper `_obfStr$(int i)` applies the inverse transformation before indexing.

### Kernel AST implementation sketch

1. **Collection phase** (visitor): Walk all `StringLiteral` nodes in user libraries, collect the string values. Skip const contexts.
2. **Injection phase**: Create a top-level `Field` with a `ListLiteral` initializer containing the (encrypted) strings. Create a `Procedure` that takes an `int` parameter and returns `_obfArr$[transform(i)]`.
3. **Replacement phase** (transformer): Replace each collected `StringLiteral` with `StaticInvocation(_obfStr$, Arguments([IntLiteral(index)]))`.

### Further reading

- JavaScript Obfuscator — string array feature documentation: https://github.com/nicolo-ribaudo/javascript-obfuscator — the `stringArray`, `rotateStringArray`, and `stringArrayEncoding` options demonstrate this exact technique
- Banescu et al. — "A Tutorial on Software Obfuscation" (2016): https://mediatum.ub.tum.de/doc/1367533/file.pdf — Section 3.2 covers data obfuscation including string tables

## 6. Multi-Layer String Encoding

### What is it?

Instead of a single transformation (XOR), apply a chain of transformations to each string. The injected decoder reverses them in the opposite order.

### Example encoding chain

```
Plaintext: "hello"

Step 1 — UTF-8 bytes:        [104, 101, 108, 108, 111]
Step 2 — XOR with key 0x5A:  [66, 95, 70, 70, 69]
Step 3 — Reverse byte array: [69, 70, 70, 95, 66]
Step 4 — Base64 encode:      "RUZGXwI="
```

The encoded value `"RUZGXwI="` is stored as a `StringLiteral` in the kernel. At runtime, the decoder:

```dart
String _decode$(String encoded) {
  final bytes = base64Decode(encoded);        // Step 4 inverse
  final reversed = bytes.reversed.toList();   // Step 3 inverse
  final decoded = reversed.map((b) => b ^ 0x5A).toList(); // Step 2 inverse
  return String.fromCharCodes(decoded);       // Step 1 inverse
}
```

### Why layering helps

Each layer forces the attacker to identify and reverse one more transformation. A single XOR is broken by frequency analysis or by finding the key literal. With layering:
- The attacker sees Base64 and decodes it — but gets reversed XOR'd bytes, not plaintext
- They recognise the reversal and undo it — but still have XOR'd bytes
- They find the XOR key and decode — finally get plaintext

Each layer is individually simple, but the composition requires understanding the full chain in order.

### Per-string variation

Each string can use a different encoding chain (e.g., string A uses XOR→reverse→Base64, string B uses XOR→Base64 without reversal). This prevents the attacker from writing a single universal decoder.

In kernel terms: inject multiple decoder procedures (or one procedure with a "mode" parameter that selects the chain).

### Further reading

- ConfuserEx string encryption — uses a combination of XOR, compression, and module initialiser injection: https://iterasec.com/blog/understanding-confuserex2-net-obfuscation-and-deobfuscation-techniques/
- Practical string obfuscation analysis: https://www.trickster.dev/post/javascript-obfuscation-techniques-by-example/

## 7. Method Outlining

### What is it?

Method outlining (also called "code extraction" or "procedure splitting") takes a contiguous slice of statements from inside a procedure body and moves them into a new synthetic procedure. The original slice is replaced with a call to the new procedure.

### Why it's useful for obfuscation

- **Fragments logical units.** A function that originally performs one coherent task is split into several functions with meaningless names. A reverser must mentally reconstruct the original grouping.
- **Inflates the call graph.** The program appears to have more functions than it actually does, making call-graph analysis more expensive.
- **Synergy with rename.** The extracted procedures get names like `_$47`, indistinguishable from original procedures.

### The variable capture problem

When extracted statements reference local variables from the enclosing scope, those variables must be passed as parameters:

```dart
// Original:
void process() {
  var x = 10;       // Statement 1
  var y = x * 2;    // Statement 2  ← references x
  print(y);         // Statement 3  ← references y
}

// After outlining statements 2-3:
int _$7(int x) {    // x is captured — becomes a parameter
  var y = x * 2;
  print(y);
  return y;          // if y is used later, must be returned
}

void process() {
  var x = 10;
  _$7(x);
}
```

### Liveness analysis

To determine which variables to capture, perform a simple analysis:

1. Collect all `VariableGet` and `VariableSet` references inside the extracted slice
2. For each referenced `VariableDeclaration`, check if it was declared *outside* the slice
3. Those declared outside are "captured" — they become parameters
4. If a captured variable is *written* inside the slice and *read* after the slice, it must be returned (or use a wrapper object)

In Dart kernel, this is straightforward because `VariableGet.variable` and `VariableSet.variable` are direct object references to `VariableDeclaration` nodes. You can check if the declaration is inside or outside the extracted range by object identity.

### Preventing AOT inlining

The Dart AOT compiler aggressively inlines small procedures. If it inlines the extracted procedure back into its caller, the obfuscation is undone. Prevent this with:

```dart
@pragma('vm:never-inline')
```

In kernel AST, this is an annotation on the `Procedure` node: a `ConstantExpression` containing an `InstanceConstant` of class `pragma` with field value `StringConstant('vm:never-inline')`.

### Further reading

- COOPS — "A Code Obfuscation Method Based on Obscuring Program Semantics" (2022): https://onlinelibrary.wiley.com/doi/10.1155/2022/6903370
- Collberg & Nagra — "Surreptitious Software: Obfuscation, Watermarking, and Tamperproofing for Software Protection" (book, 2009) — Chapter 4 covers code transformation techniques including outlining

## 8. Name Overloading

### What is it?

Name overloading assigns the *same* obfuscated identifier to multiple unrelated declarations, as long as they don't conflict at runtime. This is the opposite of the current approach (each declaration gets a unique sequential name).

### How it works

In Dart, two methods in different classes can have the same name without conflict because dispatch uses the receiver type + method name pair:

```dart
// Before obfuscation:
class UserService {
  void fetchData() { ... }    // Method A
}
class Logger {
  void writeLog() { ... }     // Method B
}

// Current rename (unique names):
class _$0 {
  void _$1() { ... }
}
class _$2 {
  void _$3() { ... }
}

// With overloading (shared names):
class _$0 {
  void _$1() { ... }     // _$1 in class _$0
}
class _$1 {               // _$1 is also a class name!
  void _$1() { ... }     // _$1 in class _$1
}
```

Now `_$1` refers to three completely unrelated things: a class, a method in `_$0`, and a method in `_$1`. A reverser cannot determine what `_$1` means without knowing the context.

### Collision safety rules

Two members can share a name only if:
1. They are in different classes (for instance members)
2. They don't have a subclass relationship (otherwise the name would be treated as an override)
3. They have compatible dispatch — e.g., a field getter and a method with the same name in the same class would conflict

In kernel terms, the safety check requires building a class hierarchy and ensuring no two members sharing a name are on the same inheritance path (`Class.supertype`, `Class.implementedTypes`, `Class.mixedInType`).

### Why it's effective

ProGuard/R8 do this extensively for Android apps. The result is that many methods across the entire app are named `a`, `b`, or `c`. Searching for `a` returns hundreds of results in unrelated classes. Manual deobfuscation becomes a contextual puzzle rather than a simple find-replace.

## 9. Integer Constant Encoding

### What is it?

Replace integer literals in the code with expressions that compute the same value at runtime.

### Techniques

**XOR split:**

```dart
// Original: 42
// Encoded: (42 ^ key) ^ key == 42 for any key
// With key = 0xCAFE:
(0xCA94 ^ 0xCAFE)  // computes to 42 at runtime
```

In kernel: `InstanceInvocation(IntLiteral(0xCA94), '^', Arguments([IntLiteral(0xCAFE)]))`

**Arithmetic split:**

```dart
// Original: 100
// Encoded: 17 * 6 - 2
```

**MBA encoding:**

```dart
// Original: n
// Encoded: ((n | k) - (k & ~n))  where k is random
// This identity holds because: (n | k) - (k & ~n) == n for all k
```

Proof: `n | k` sets all bits that are in `n` or `k`. `k & ~n` gives the bits in `k` that are NOT in `n`. Subtracting those leaves only the bits of `n`.

### Const context restriction

In Dart, `const` expressions are evaluated at compile time. You cannot replace a constant integer with a function call or operator expression that the compiler doesn't know how to fold:

```dart
const x = 42;           // Cannot replace 42 with (0xCA94 ^ 0xCAFE)
                         // because ^ is not a const operation on int

var y = 42;             // CAN replace — y is not const
final z = 42;           // CAN replace — final is runtime-evaluated
```

The transformer must check for const context (same `_constDepth` / `_annotationDepth` tracking already used by string_encrypt).

### AOT constant folding risk

The Dart AOT compiler performs constant propagation and folding. If both operands of `^` are `IntLiteral`, the compiler may fold `0xCA94 ^ 0xCAFE` back to `42`, undoing the obfuscation.

To prevent this, one operand can be "laundered" through a variable:

```dart
final _k = 0xCAFE;  // not const, so AOT cannot fold across this
var y = (0xCA94 ^ _k);
```

Or use a top-level `final` field with a runtime initialiser. The trade-off is a real runtime cost (memory read instead of immediate constant).

### Optimization resistance

**Verdict: WEAK unless runtime-laundered.** If both operands of `(n ^ k) ^ k` are `IntLiteral`, the Simplification pass folds them back to `n` in a single step. To survive, at least one operand must be a runtime value (e.g., a `final` field read or function call result). This adds real runtime cost (memory read per encoded integer). See [optimization-resistance.md](optimization-resistance.md).

- Plzin MBA blog post (covers constant encoding): https://plzin.github.io/posts/mba

## 10. Scope-Aware Local Variable Renaming

### What is it?

Rename local variables and function parameters to short, reused names. Unlike class/field/procedure renaming (which is global), local names can be reused across unrelated scopes because they're only visible within their declaring scope.

### Why it's safe in Dart kernel

Dart kernel uses **identity-based** variable references, not name-based:

```
VariableDeclaration('counter', type: InterfaceType(int))
  │
  ├── VariableGet(variable: ──────────────> same object
  │
  └── VariableSet(variable: ──────────────> same object, value: ...)
```

`VariableGet.variable` is a direct pointer to the `VariableDeclaration` object. The `.name` field on `VariableDeclaration` is used only for:
- Debug info / stack traces
- Decompiler output
- Source-map generation

Changing `.name` from `"counter"` to `"a"` does not affect runtime behaviour in any way. The VM never looks up variables by name string — it uses the object reference.

### Name reuse across scopes

```dart
// Before:
void process() {
  var counter = 0;
  for (var item in list) {
    var result = transform(item);
    counter += result;
  }
  var message = 'Done: $counter';
  print(message);
}

// After:
void process() {
  var a = 0;
  for (var a in list) {      // different scope — can reuse 'a'
    var b = transform(a);
    a += b;                   // wait — this 'a' is the loop variable, not counter!
  }
  var a = 'Done: $a';        // yet another 'a'
  print(a);
}
```

In kernel, each `VariableDeclaration` is a distinct object even if they share the `.name` string. So reusing `"a"` across scopes is completely safe — each `VariableGet` still points to its correct declaration.

This makes decompiled output extremely confusing because the same name `a` means completely different things in different contexts.

## 11. Key Dart Kernel Constraints

### Things you must know when implementing any pass

**Const context:**

Expressions inside `ConstantExpression`, annotation lists, and `const` constructors are evaluated at compile time. You cannot replace them with runtime computations. Every transformer must track const depth.

```
ConstantExpression(StringConstant("hello"))  // DO NOT transform
StringLiteral("hello")                       // OK to transform
```

**Async lowering:**

By the time kernel is serialised, `async`/`async*`/`sync*` procedures have been lowered by the front-end's continuation transformer into complex state machines with `_AsyncAwaitCompleter`, `_awaitHelper`, etc. These bodies are fragile and should generally be skipped by obfuscation passes. Check `procedure.function.asyncMarker != AsyncMarker.Sync`.

**Canonical names:**

Every `Library`, `Class`, and `Member` has a `CanonicalName` in a global tree. After renaming, these must be invalidated (`reference.canonicalName?.unbindAll()`) so the `BinaryPrinter` recomputes them. Forgetting this causes serialisation errors.

**`dart:` libraries:**

Never transform nodes in `dart:core`, `dart:async`, etc. The SDK libraries are shared across all programs and modifications would break the runtime. Every pass must check `library.importUri.scheme == 'dart'`.

**`@pragma('vm:never-inline')`:**

When injecting synthetic procedures (for outlining, string decoding, etc.), add this pragma to prevent the AOT compiler from inlining them back into callers, which would undo the obfuscation.

**Two's complement integers:**

Dart `int` is 64-bit on native targets (AOT/JIT) but 53-bit on web (dart2js). MBA and integer encoding techniques that rely on overflow wrapping will produce different results on web. For now, target native only.
